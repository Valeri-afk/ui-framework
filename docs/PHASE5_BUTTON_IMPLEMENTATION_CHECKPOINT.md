# Phase 5 — Button Implementation Checkpoint

## Status

Concrete design checkpoint for the first provided component implementation.

This document is intentionally narrower than `PHASE5_COMPONENT_ARCHITECTURE.md`.
It records the current Button contract before implementation begins.

---

# 1. Component identity

Preferred initial implementation:

```text
Button : Node
```

`PanelNode` is not required merely because Button has text or other visual primitives.

Button may use internal visual primitives without making them structural NodeTree children.

A future change to `PanelNode` remains possible if concrete requirements demonstrate genuine child ownership/layout composition.

---

# 2. Responsibility boundary

## Framework owns

```text
hit-test
pointer target selection
mouse down/up/click recognition
pointer capture
focus
input routing
event propagation
Node geometry
Node visibility/enabled state
update/render traversal
mutation safety
text primitive mechanics
```

## Button owns

```text
pressed semantic state
activation semantics
Button presentation
Button visual variants
press presentation animation
local arrangement of its own visual content
```

Button must not reimplement generic input or event dispatching.

---

# 3. Semantic state

Primary transient state:

```text
pressed
```

`pressed` is component state used to drive presentation.

It is not a duplicate of generic `captured` state.

The intended pointer relationship is:

```text
left MouseDown targeting Button
    -> pressed = true

MouseUp / pointer cancellation
    -> pressed = false
```

The final cancellation path must account for framework pointer capture cancellation, node invalidation, disabled/hidden state and structural removal rather than relying only on MouseLeave.

---

# 4. Activation

Button exposes a semantic action:

```text
activate()
```

`MouseClickEvent` is generated by the framework after its generic pointer sequence has established a click target. Button consumes that semantic event rather than reproducing click recognition.

The semantic activation operation should remain usable by other interaction paths, such as future keyboard activation or deliberate programmatic invocation.

Do not create a Button-specific callback subsystem for MouseDown/MouseUp/MouseEnter/etc. Use the existing framework event system.

---

# 5. Node defaults

Button is expected to use framework-recognized Node state rather than maintain duplicates.

Likely defaults:

```text
visible = true
enabled = true
focusable = true
capturable = true
```

These are framework properties, not Button-specific state.

Exact default values should follow the existing Node API and implementation rather than duplicating constants unnecessarily.

---

# 6. Content

Initial concrete scope:

```text
text
```

The component API should be semantic:

```cpp
setText(...)
```

not renderer-dependent:

```cpp
setText(..., SDL_Renderer*)
```

Renderer/resource details remain framework implementation concerns.

Future content variants may include:

```text
icon
text + icon
```

but IconNode/IconPrimitive is not required for the first Button slice.

Do not create `TextButton` merely to represent the text-only form.

---

# 7. Visual variants

The old Button implementation established useful presentation variants:

```text
FILLED
OUTLINED
TEXT
```

These should remain variants of one Button rather than separate component classes.

The variant controls presentation. It does not change the semantic identity of Button.

---

# 8. State-dependent presentation

Button presentation is derived from framework state + Button state.

Candidate presentation states include:

```text
normal
hovered
pressed
focused
 disabled
```

The exact style system is intentionally not defined here.

Do not introduce a generic CSS-style style engine merely to support Button.

---

# 9. Press animation

The previous Button implementation contained a useful press-scale presentation effect:

```text
pressed
    -> target visual scale
    -> interpolated current scale in update(dt)
    -> draw using the current visual scale
```

This behavior is retained as a valid component-owned presentation feature.

The animation must not mutate the framework's actual layout size just to achieve the visual effect.

Conceptually:

```text
Node actual geometry
    !=
Button visual presentation scale
```

The exact default scale, speed and public configuration API should be chosen during implementation from the existing behavior rather than copied blindly.

No global AnimationManager is introduced for this feature.

---

# 10. Local content layout

Button may calculate the layout of its own visual primitives without being a PanelNode.

Example:

```text
Button rect
    -> content rect
       -> text rect
       -> future icon rect
```

This is component-local presentation layout, not generic NodeTree child layout.

The Button implementation should therefore not require a universal child layout engine solely for text/icon composition.

---

# 11. Text implementation

The existing `TextNode` remains the public framework primitive.

For internal use by components, text measurement/rendering should not require a client-owned `TextService`.

Preferred implementation direction:

```text
internal reusable text representation/primitive
    -> measure
    -> draw

TextNode : Node
    -> adapts that implementation to NodeTree

Button
    -> may use the same internal text machinery without adding a TextNode
       to its structural child tree
```

This internal representation should remain private to the framework until concrete reuse proves that a wider abstraction is justified.

Do not introduce `TextService`, `TextManager`, `ITextRenderer`, or similar public service layers merely to solve Button text.

---

# 12. Explicit non-goals for first Button slice

Do not introduce as part of the initial Button implementation:

```text
ActionNode
ControlNode hierarchy
TextButton / separate text-only type
IconNode solely for Button
universal content model
CSS-like style system
resource manager
animation manager
renderer parameter in semantic text API
custom callback subsystem
```

`IconButton`, `ToggleButton`, `Fab` and other specialized action components will be evaluated after the basic Button implementation exposes real shared behavior.

---

# 13. Evidence from previous implementation

The historical Button implementation remains valuable as behavioral evidence.

It already demonstrated:

```text
text content
filled / outlined / text variants
border radius presentation
press state
press-scale animation
text measurement and centering
mouse interaction callbacks
```

Those behaviors should be evaluated individually rather than copied as architecture.

In particular, old renderer-dependent text setters and old component-specific callback APIs are intentionally not part of the new contract.

---

# 14. Implementation order

Recommended first slice:

```text
1. Internal text measurement/rendering primitive, only as much as Button requires.
2. Adapt TextNode to the shared text implementation without changing its public semantics unnecessarily.
3. Implement Button as Node.
4. Implement text content.
5. Implement Filled/Outlined/Text variants.
6. Implement framework-event-driven pressed state.
7. Implement activate semantics.
8. Preserve the press-scale presentation behavior.
9. Implement Button-local content measurement/arrangement.
10. Validate against existing Node/layout/input/render contracts.
```

Do not implement IconButton/ToggleButton abstractions until this concrete slice is understood.
